4. Cada hallazgo explicado

Sin límite de peticiones (posible denegación de servicio) · Corregido

javascript/NoRateLimitingForExpensiveWebOperation · CWE-770 · antes: 1 · después: 0

Lo que dice Snyk: Expensive operation (a file system operation) is performed by an endpoint handler which does not use a rate-limiting mechanism. It may enable the attackers to perform Denial-of-service attacks. Consider using a rate-limiting middleware such as express-limit.

Qué significa: El servidor hacía una operación costosa (leer el disco) en cada petición y no limitaba cuántas peticiones podía enviar una misma IP. Un atacante podría inundarlo de peticiones para dejarlo sin recursos (ataque DoS).

Qué se hizo: Se añadió un limitador por IP de tipo token bucket: 30 peticiones/s con ráfagas de 60; al superarlo responde 429 Too Many Requests con Retry-After, y se cuenta en la métrica http_requests_rate_limited_total. Además, el HTML se carga en memoria al arrancar y se recarga solo cuando cambia el archivo, así que ninguna petición toca el disco. Verificado con 2 pruebas nuevas en la suite 03.

Path Traversal (recorrido de rutas) · Corregido

javascript/PT · CWE-23 · antes: 2 · después: 0

Lo que dice Snyk: Unsanitized input from a command line argument flows into fs.readFileSync, where it is used as a path. This may result in a Path Traversal vulnerability and allow an attacker to read arbitrary files.

Qué significa: La herramienta que convierte la documentación a HTML usaba el texto escrito en la línea de comandos directamente como ruta de archivo. Con algo como "../../archivo" podría leer o sobrescribir archivos fuera del proyecto.

Qué se hizo: La herramienta ahora solo acepta los tres documentos de una lista cerrada (README.md, RENDIMIENTO.md y SNYK.md). Las rutas de lectura y escritura salen de esa lista, nunca del texto del usuario; cualquier otro valor se rechaza. También se escapa el título de la página.

Transmisión en texto claro (HTTP en lugar de HTTPS) · Riesgo aceptado (mitigado)

javascript/HttpToHttps · CWE-319 · antes: 1 · después: 1

Lo que dice Snyk: http.createServer uses HTTP which is an insecure protocol and should not be used in code due to cleartext transmission of information. Data in cleartext in a communication channel can be sniffed by unauthorized actors. Consider using the https module instead.

Qué significa: El servidor usaba solo HTTP, sin cifrado. Si se expusiera en una red, alguien podría leer el tráfico.

Qué se hizo: Se añadió soporte HTTPS: con las variables TLS_CERT y TLS_KEY el servidor usa https.createServer con TLS 1.2 como mínimo (comprobado con TLS 1.3 y una prueba automática que verifica el certificado). Sin certificado, el modo HTTP se mantiene solo para uso local: escucha en 127.0.0.1 y el tráfico no sale del equipo. Snyk sigue marcando la línea porque el modo HTTP existe; en producción se usa HTTPS o un proxy inverso con TLS delante.

HTTP en las pruebas automáticas · Falso positivo

javascript/HttpToHttps/test · CWE-319 · antes: 6 · después: 8

Lo que dice Snyk: http.get uses HTTP which is an insecure protocol and should not be used in code due to cleartext transmission of information. Data in cleartext in a communication channel can be sniffed by unauthorized actors. Consider using the https module instead.

Qué significa: Las pruebas se conectan por HTTP al servidor de CyberShield que ellas mismas arrancan en el propio equipo (127.0.0.1).

Qué se hizo: No hay riesgo: es tráfico local entre la prueba y el servidor de prueba, sin datos reales. El modo cifrado se verifica aparte con su propia prueba HTTPS. Snyk etiqueta la regla con "/test" porque sabe que es código de pruebas.

Contraseña escrita en el código · Falso positivo

javascript/NoHardcodedPasswords/test · CWE-798, CWE-259 · antes: 1 · después: 1

Lo que dice Snyk: Do not hardcode passwords in code. Found hardcoded password used in pw.

Qué significa: Snyk detecta texto que parece una contraseña dentro de una prueba.

Qué se hizo: Son contraseñas ficticias ("aaaaaaaaaaaa", "xpasswordx"…) que se usan para comprobar que el medidor de fortaleza del juego las clasifica bien. No dan acceso a nada.

Configuración TLS insegura en una prueba · Corregido

javascript/InsecureTLSConfig/test · antes: 0 · después: 0 (apareció en un análisis intermedio y se corrigió)

Qué significa: La prueba de HTTPS aceptaba cualquier certificado (rejectUnauthorized: false).

Qué se hizo: Ahora la prueba confía solo en el certificado de prueba que genera, con la opción ca, y valida el nombre localhost / 127.0.0.1. Ya no desactiva ninguna comprobación.

5. Glosario

Snyk Code (SAST)
Análisis estático del código fuente: lee el código sin ejecutarlo y busca patrones peligrosos (inyecciones, XSS, rutas sin validar, secretos…), siguiendo el recorrido de los datos desde donde entran (source) hasta donde se usan (sink).
Snyk Open Source (SCA)
Análisis de composición del software: revisa las librerías de terceros (dependencias) y sus versiones contra una base de datos de vulnerabilidades conocidas.
Severidad HIGH / MEDIUM / LOW
Gravedad estimada por Snyk. HIGH: explotable y con mucho impacto, hay que corregirla ya. MEDIUM: riesgo real en ciertas condiciones. LOW: impacto bajo o difícil de explotar.
CWE
Common Weakness Enumeration: catálogo internacional de tipos de debilidades de software (por ejemplo, CWE-23 = Path Traversal, CWE-319 = transmisión en texto claro, CWE-770 = recursos sin límite).
Falso positivo
Algo que la herramienta marca como problema pero que, en el contexto real, no se puede explotar. Se documenta con su justificación.
Riesgo aceptado (mitigado)
Un riesgo real pero controlado: existe una medida que lo reduce y se acepta conscientemente el resto, con justificación.
Path Traversal
Usar texto controlado por alguien como ruta de archivo, lo que permite salir de la carpeta prevista con "../" para leer o escribir otros archivos.
DoS y rate limiting
Denegación de servicio: saturar un servidor con peticiones. El rate limiting limita cuántas peticiones acepta de cada cliente por segundo.
HTTP / HTTPS / TLS
HTTP envía los datos sin cifrar. HTTPS los cifra con TLS (la versión 1.2 o superior se considera segura).
Código 1 de Snyk
Snyk termina con el código 1 cuando hay algún hallazgo, aunque sea un falso positivo. No significa que el análisis fallara.

6. Cómo repetir este análisis

  1. npm run snyk:cobertura: debe dar 100 % de JavaScript.
  2. snyk test: dependencias.
  3. snyk code test: código fuente.
  4. node herramientas/informe-snyk.js: regenera este informe. En Windows también puedes usar seguridad\ejecutar-snyk.bat.

Nota: el CLI de Snyk solo permite marcar hallazgos como "ignorados" desde la web de Snyk o dentro de un repositorio conectado. Por eso los falsos positivos siguen apareciendo en la consola, y su justificación queda en este informe y en comentarios del propio código.
